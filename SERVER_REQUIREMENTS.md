# Системные требования для развёртывания на арендованном сервере

## 1. Назначение и схема развёртывания

Текущее приложение разворачивается как один Node.js-процесс, который:
- отдаёт собранный React UI из `ui/dist`;
- принимает HTTP API-запросы;
- запускает внешние утилиты `yt-dlp`, `ffmpeg`, `python run_whisperx.py`, `python split_whisperx.py`;
- хранит рабочие файлы, временные загрузки, аудит и секреты на локальном диске в каталоге `work/`.

Внешняя база данных и отдельная очередь задач не требуются.

## 2. Рекомендуемая платформа

- ОС: `Ubuntu Server 22.04 LTS` или `Ubuntu Server 24.04 LTS`
- Архитектура: `x86_64`
- Тип диска: `SSD/NVMe`
- Размещение: `1 сервер = 1 экземпляр приложения`

Linux для этого проекта предпочтителен: проще установка `ffmpeg`, `yt-dlp`, Python-окружения и GPU-драйверов.

## 3. Аппаратные требования

Ниже указаны рабочие ориентиры для текущего кода. Это инженерная оценка по фактическому пайплайну `yt-dlp -> ffmpeg -> WhisperX large-v2 -> split -> LLM`.

### Минимум для режима только прямого скачивания видео

- `2 vCPU`
- `4 GB RAM`
- `20 GB SSD`
- GPU не требуется

### Минимум для полного пайплайна без GPU

- `8 vCPU`
- `16 GB RAM`
- `50 GB SSD/NVMe`
- GPU не требуется, но транскрибация будет медленной

### Рекомендуемо для прод-использования полного пайплайна

- `8-16 vCPU`
- `32 GB RAM`
- `100 GB+ NVMe`
- `NVIDIA GPU` с поддержкой `CUDA`
- `10-16 GB VRAM` как практичный ориентир для WhisperX с моделью `large-v2`

### Ограничение по параллелизму

Без отдельной очереди и лимитов одновременной обработки рекомендуется:
- не более `1-2` одновременных задач транскрибации;
- не более `2-4` одновременных задач прямого скачивания, если сервер слабый по диску и сети.

## 4. Обязательное системное ПО

- `Node.js 18+`
- `npm`
- `Python 3.10+`
- `ffmpeg` в `PATH`
- `yt-dlp` в `PATH`

### Python-окружение

Для полного пайплайна должны быть установлены:
- `whisperx`
- зависимости `torch` / `pyannote` из окружения `whisperx`
- при работе с `Kick` и похожими источниками: `curl_cffi`

Если используется GPU, версия `torch` и сборка `whisperx` должны совпадать с установленной версией CUDA-драйвера.

## 5. Сетевые требования

### Входящие подключения

- `80/tcp` и `443/tcp`, если приложение публикуется через `nginx` или `caddy`
- либо `3000/tcp`, если Node.js-процесс открыт напрямую

### Исходящие подключения

Серверу нужен исходящий HTTPS-доступ:
- к выбранному LLM-провайдеру: `OpenAI`, `DeepSeek`, `xAI`, `Gemini`
- к `Hugging Face` для diarization/pyannote
- к видео-источникам: `VK`, `YouTube`, `Twitch`, `Kick`
- к `GitHub`, если используются remote-components `yt-dlp`

DNS-резолвинг должен работать стабильно.

## 6. Требования к файловой системе

Процесс приложения должен иметь права на чтение/запись:
- в каталог проекта;
- в `work/`;
- в `work/<job-id>/`;
- в `work/downloads/`;
- в `work/audit/`.

Если используется `COOKIES_FILE`, файл cookie должен быть доступен на чтение для пользователя, от которого запускается Node.js-процесс.

### Оценка диска

При планировании диска нужно учитывать:
- временные видеофайлы `yt-dlp`;
- промежуточный `audio.wav`;
- txt-транскрипты и чанки;
- готовые файлы прямого скачивания;
- сохранение последних `20` job-каталогов по умолчанию.

Практическое правило:
- закладывать минимум `3x` от максимального размера одного обрабатываемого ролика на каждый активный job;
- для прямого скачивания через merge лучше считать `до 2x` размера итогового файла на время обработки.

## 7. Переменные окружения

### Обязательные для полного пайплайна пересказа

- `HF_TOKEN`
- один из ключей LLM:
  - `OPENAI_API_KEY`
  - `DEEPSEEK_API_KEY`
  - `GROK_API_KEY`
  - `GEMINI_API_KEY`

### Не обязательны, если нужен только режим скачивания видео

Если сервер будет использовать только вкладку прямого скачивания видео:
- `HF_TOKEN` не нужен;
- LLM API-ключи не нужны;
- WhisperX можно не устанавливать.

### Важные опциональные переменные

- `PORT`
- `WORK_ROOT`
- `UI_DIST`
- `YTDLP_BIN`
- `FFMPEG_BIN`
- `PYTHON_BIN`
- `WHISPERX_SCRIPT`
- `SPLIT_SCRIPT`
- `COOKIES_FILE`
- `YTDLP_YOUTUBE_PO_TOKEN`

## 8. Эксплуатационные ограничения текущей реализации

### Один экземпляр приложения

Текущая реализация рассчитана на один инстанс:
- статусы job хранятся в памяти процесса;
- рабочие артефакты лежат на локальном диске;
- при рестарте процесса активные job теряют runtime-состояние.

Горизонтальное масштабирование без доработок не рекомендуется.

### Нет встроенной аутентификации

Приложение нельзя безопасно публиковать в интернет без внешней защиты. Для арендуемого сервера обязательно одно из решений:
- reverse proxy с Basic Auth;
- доступ только через VPN;
- IP allowlist;
- SSO/внешний auth layer.

### Секреты пишутся на диск

Нужно учитывать, что в текущей реализации:
- API-ключи сохраняются в `work/env-secrets.json`;
- аудит-логи содержат снимок токенов на момент запуска job.

Это значит:
- доступ к `work/` должен быть ограничен;
- резервные копии нужно считать секретными;
- нельзя хранить этот каталог в общедоступных шарингах.

## 9. Рекомендуемая схема прод-развёртывания

- `Ubuntu 24.04 LTS`
- `Node.js 20 LTS`
- `Python 3.10/3.11`
- `ffmpeg`
- `yt-dlp`
- отдельное Python virtualenv с `whisperx`
- `nginx` или `caddy` перед приложением
- `systemd` или `pm2` для автозапуска
- `HTTPS`
- ограничение доступа по auth/VPN

## 10. Краткий итог

Для надёжного размещения этого проекта на арендованном сервере разумный базовый вариант такой:
- `8 vCPU`
- `32 GB RAM`
- `100 GB NVMe`
- `Ubuntu 24.04 LTS`
- `Node.js 20 LTS`
- `Python 3.10+`
- `ffmpeg`, `yt-dlp`, `whisperx`
- `NVIDIA GPU` желательна, если нужен быстрый полный пайплайн пересказа

Если GPU не будет, приложение всё равно можно развернуть, но скорость транскрибации станет главным узким местом.
